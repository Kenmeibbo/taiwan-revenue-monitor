# Pure-program cloud revenue updates

The public Sites website is updated by `.github/workflows/revenue-sync.yml` using Python standard-library HTTP calls. No AI model, Codex automation, paid runner or API key is used. `start.bat` and the local Python server are unchanged; this cloud workflow does not depend on the user's PC.

Recent revenues use TWSE `https://openapi.twse.com.tw/v1/opendata/t187ap05_L` (listed) and TPEx `https://www.tpex.org.tw/openapi/v1/mopsfin_t187ap05_O` (OTC) when their `資料年月` matches the requested month. Stale/mismatched/failed exports fall back to official MOPS per-month reports to preserve partial current-month coverage; history uses official per-month reports as well. OpenAPI export dates are not company announcement times. The government holiday calendar is a separate official CSV source.

Nominal frequency: every five minutes, 24 hours a day, including overnight, at minutes 02,07,12,17,22,27,32,37,42,47,52,57 to avoid top-of-hour traffic. The server evaluates calendar dates in Asia/Taipei, never from a caller-supplied clock, and records one completed capture per five-minute bucket. Duplicate triggers do not refetch and a global lease prevents overlap across buckets. GitHub scheduled jobs can be delayed or missed under load; this is a nominal polling interval, not an exact delivery guarantee. The website itself rereads stored data every minute without triggering upstream fetches.

Collection dates: 1-11 inclusive every month. If the 11th is a holiday or weekend, add only the next Mon-Fri working day, skipping consecutive holidays. The Sites server uses official DGPA calendar dataset 14718 and rejects incomplete/unavailable annual calendars. Outside those dates the workflow checks policy and skips official revenue/announcement sources. Opening or filtering the website reads stored data without upstream fetches. The manual refresh button follows the same date/slot policy. Later corrections outside these dates wait for next month's window. Latest revenue and announcement feeds are checked each capture; the preceding, completed revenue month is rechecked at most daily. Missing/partial previous-month data is fetched sooner to finalize history. Identical revenue content updates snapshot check time/completeness without deleting and reinserting company rows. Increased polling does not use AI tokens, but normal source/site/GitHub quotas and availability still apply.

The workflow polls the site's read-only policy before performing a POST refresh. A push changing this workflow or the scheduler scripts runs unit tests, a live policy check, and the same gated sync to verify the complete cloud pipeline. Monthly receipt-only commits do not match the push path filter. `Run workflow` in GitHub Actions follows the same date/slot restrictions. Check workflow runs for failures. Source failures retain existing data and produce a failed job; new-high counts never use incomplete history. A successful push or manual run proves execution works, not that a schedule event has fired: verify an actual schedule-triggered run separately.

GitHub disables scheduled workflows in idle public repos after 60 days. To avoid that limit, the workflow saves one genuine successful synchronization receipt per month in `.github/revenue-sync-status.json`. Only the sync job has `contents: write`; it uses GitHub's short-lived built-in token to commit the receipt, not a personal token. Branch protection or Actions write restrictions may prevent the receipt commit: fix the reported job failure rather than assuming the schedule remains active forever. Receipt-only commits can trigger other existing repository deployment integrations (such as Render auto-deploy) if still enabled.

The old Sites AI task, "哲緯台股月營收自動同步", was verified disabled through Sites metadata on 2026-10-07. Do not re-enable it or add an external scheduler for this configuration.

Latest-month updates also reconcile official announcement events with the company's `t05st10_ifrs` JSON report, instead of relying only on delayed monthly summary exports. `sync_revenue.py` drains bounded pending batches through `POST /api/scheduled-refresh?drain=1`. A previous-month timeout is a warning, not a reason to discard current-month progress. Missing/failed company details retain their prior verified values. A successful run is not evidence that all original filing timestamps have been recovered: archived major-announcement times are explicitly distinguished, and unresolved original times remain pending. The site offers a visitor-triggered background fallback when stored data is stale; that fallback does not establish unattended scheduling. As of the investigation on 2026-10-07, no schedule-triggered GitHub run had been observed, despite successful push-triggered end-to-end runs. Do not represent configured cron timing as proven execution until a genuine schedule event is recorded.
